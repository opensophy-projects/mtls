- **CLI-режим** — все операции доступны из командной строки, без TUI

- **Шифрование ключа CA** — опциональная защита паролем приватного ключа корневого CA
- **Раздельные bundle на сервис** — `BUNDLE_MODE=per-service` создаёт отдельный `clients-bundle-<service>.crt` для каждого сервиса вместо одного общего bundle
- **Уведомления** — webhook + Telegram-уведомления об истекающих/истёкших сертификатах
- **Резервное копирование и восстановление** — `ca backup` / `ca restore` для полного архивирования CA + БД + конфига
- **Продление сертификатов** — `cert renew` перевыпускает сертификат с тем же именем
- **Проверка сертификатов** — `cert verify` проверяет цепочку и выводит детали
- **Проверка цепочки** — все вновь подписанные сертификаты проверяются по полной цепочке перед сохранением
- **Валидация YAML** — сгенерированный конфиг Traefik структурно проверяется
- **Блокировка БД** — `flock` предотвращает повреждение базы данных при concurrent-доступе
- **Полное удаление сервиса** — `service delete-full` отзывает все сертификаты, удаляет файлы, промежуточные CA, блоки Traefik и патчи

## Что делает скрипт

`mtls.sh` — bash-менеджер mTLS-сертификатов для reverse-proxy **Traefik**. Он позволяет:

- создавать и управлять корневым CA (Certificate Authority)
- выпускать, продлевать, отзывать и удалять клиентские сертификаты (`.crt`, `.key`, `.p12`)
- автоматически генерировать конфигурацию Traefik с настройками mTLS
- работать в двух режимах интеграции с Traefik: создание нового роутера или патч существующего
- проверять истекающие сертификаты и отправлять уведомления
- создавать резервные копии и восстанавливать CA + базу данных
- контролировать кто может использовать скрипт (список доступа)

Скрипт не требует сторонних инструментов кроме `openssl` и `python3` — оба присутствуют в любом современном Linux-окружении.

## Зависимости и требования

| Зависимость | Где используется | Обязательна |
|---|---|---|
| `openssl` | Генерация CA, CSR, подпись сертификатов, CRL, PKCS#12 | Да |
| `python3` | JSON-база данных, YAML-патчинг конфигов Traefik, журнал аудита | Да |
| `bash` >= 4 | Сам скрипт | Да |
| `flock` | Блокировка БД (предотвращает повреждение при concurrent-доступе) | Да (обычно в `util-linux`) |
| `curl` | Webhook / Telegram-уведомления | Только для уведомлений |
| `ip` (iproute2) | Определение IP-адреса хоста для Traefik target | Нет (fallback: `172.17.0.1`) |

При запуске скрипт автоматически проверяет наличие `openssl` и `python3`. Если они отсутствуют, предлагает установить их через `apt-get`, `yum`, `apk` или `brew`.

## Запуск

### Интерактивный TUI

```bash
chmod +x mtls.sh
sudo ./mtls.sh
```

### CLI-режим

```bash
sudo ./mtls.sh ca create --cn "My-CA" --days 3650
sudo ./mtls.sh service add --name myapp --domain myapp.example.com --target http://localhost:3000
sudo ./mtls.sh cert issue --service myapp --name alice --days 365 --note "iPhone Alice" --pass secret123
sudo ./mtls.sh cert list
```

> `sudo` нужен, если пути CA и Traefik находятся в `/etc/`. Для локального тестирования (пресет `p3`) `sudo` не нужен.

## Управление сервисами

**Меню → 4** или CLI-команды `service`.

Сервис — логическая единица, которой выдаются сертификаты. Каждый сервис соответствует одному защищённому ресурсу в Traefik.

### Режим `new`

Создаёт новый роутер и сервис в конфиге Traefik:

```
Имя сервиса    → myapp
Домен          → myapp.example.com
Target URL     → http://localhost:3000
```

В сгенерированном `mtls-manager.yml` появятся:

```yaml
http:
  routers:
    myapp-mtls:
      rule: "Host(`myapp.example.com`)"
      entryPoints:
        - websecure
      service: myapp-mtls
      tls:
        options: mtls-myapp

  services:
    myapp-mtls:
      loadBalancer:
        servers:
          - url: "http://172.17.0.1:3000"
```

> `localhost` и `127.0.0.1` в target автоматически заменяются на IP шлюза хоста (определяется через `ip route`).

### Режим `patch`

Добавляет mTLS-опцию к **уже существующему** роутеру в другом YAML-файле Traefik (например, в конфиге Dokploy).

```
Файл конфига  → /etc/dokploy/traefik/dynamic/dokploy.yml
Роутер        → my-existing-router
```

При создании первого сертификата для этого сервиса скрипт патчит указанный файл:

```yaml
# До патча:
my-existing-router:
  tls: {}

# После патча:
my-existing-router:
  tls:
    options: mtls-myapp
```

При удалении сервиса patch снимается автоматически.

### Полное удаление

`service delete-full` (или меню → 4 → 5) выполняет полную очистку:
- Отзыв и удаление ВСЕХ клиентских сертификатов сервиса
- Удаление клиентских файлов с диска
- Удаление ВСЕХ каталогов промежуточных CA сервиса
- Удаление сгенерированного блока роутера/сервиса Traefik (режим new)
- Удаление mTLS-патча из внешнего конфига (режим patch)
- Удаление сервиса из базы данных

## Операции с сертификатами

### Выпуск сертификата

**Меню → 1** или `cert issue`.

Порядок действий:
1. Выбрать сервис из списка
2. Задать имя сертификата (латиница, без пробелов — пробелы заменяются на `-`)
3. Указать срок действия (по умолчанию: значение из настроек, стандарт 365 дней)
4. Добавить заметку (для кого / чего выдан)
5. Задать пароль для `.p12`-файла (можно оставить пустым)

Скрипт последовательно:
1. Генерирует 2048-битный RSA-ключ клиента
2. Создаёт CSR
3. Создаёт промежуточный CA для этого клиента (подписан корневым CA)
4. Подписывает клиентский сертификат промежуточным CA
5. Проверяет цепочку сертификата
6. Создаёт `.p12`-bundle (ключ + сертификат + корневой CA)
7. Перестраивает bundle-файл
8. Обновляет конфиг Traefik
9. Применяет патч (если сервис в режиме patch)

### Структура выходных файлов

```
/etc/traefik/certs/mtls/clients/
└── <service>/
    └── <cert-name>/
        ├── client.key   — приватный ключ клиента
        ├── client.crt   — сертификат клиента
        └── client.p12   — bundle для импорта
```

### Продление сертификата

`cert renew --uid UID [--days D]` — только CLI.

Отзывает старый сертификат и перевыпускает новый с тем же именем и сервисом. Заметка и пароль сохраняются.

### Проверка сертификата

`cert verify --uid UID` — только CLI.

Показывает детали сертификата (серийный номер, субъект, эмитент, даты действия) и проверяет цепочку по промежуточному CA + корневому CA.

### Отзыв и удаление

**Меню → 3** или `cert revoke` / `cert delete`.

Удаление происходит в **два шага** (защита от случайного удаления):

**Шаг 1 — Отзыв:**
Устанавливает флаг `revoked=1` в БД, промежежуточный CA этого клиента исключается из `clients-bundle.crt`, конфиг Traefik обновляется. Сертификат перестаёт работать немедленно — без перезагрузки Traefik.

**Шаг 2 — Удаление файлов (при повторном входе или `cert delete`):**
Удаляет директорию с `client.key`, `client.crt`, `client.p12`, директорию промежуточного CA и запись из БД.

### Статусы сертификатов

| Статус | Условие | Цвет |
|---|---|---|
| АКТИВЕН | Действует, > 30 дней до истечения | Зелёный |
| СКОРО (Nд) | Истекает менее чем через 30 дней | Жёлтый |
| ИСТЁК | Дата истечения в прошлом | Красный |
| ОТОЗВАН | Поле `revoked=1` в БД | Красный |

## Проверка истечения и уведомления

**Меню → 8** или `cert scan`.

Проверяет все неотозванные сертификаты и сообщает об истекающих (в пределах `EXPIRY_WARN_DAYS`) и истёкших. Если настроены уведомления webhook или Telegram, отправляется предупреждение.

Настройка уведомлений (меню → 6 → 8 или `config set`):
- `WEBHOOK_URL` — POST JSON `{title, body}` на этот URL
- `TELEGRAM_BOT_TOKEN` + `TELEGRAM_CHAT_ID` — отправка сообщения через Telegram Bot API

## Создание CA

**Меню → 5** или `ca create`.

Создаёт корневой CA при первом запуске или пересоздаёт его при необходимости.

```
Имя CA (CN)            → mTLS-Root-CA
Срок действия (дней)   → 3650
Шифровать ключ?        → да/нет
```

Генерирует:
- `ca.key` (4096 бит RSA) — приватный ключ, права 600
- `ca.crt` — самоподписанный корневой сертификат
- `index.txt`, `serial`, `index.txt.attr` — база данных CA для OpenSSL
- `crl.pem` — список отзыва (изначально пустой)
- `openssl-ca.cnf` — конфигурационный файл OpenSSL

> Пересоздание CA аннулирует все ранее выпущенные сертификаты.

### Шифрование ключа CA

Если шифрование включено, приватный ключ CA защищён паролем (AES-256). Пароль должен быть предоставлен через:
- Интерактивный запрос (TUI / `ca create --encrypt`)
- Переменную окружения `MTLS_CA_PASSPHRASE` (для CLI / автоматизации)

## Резервное копирование и восстановление

**Меню → 9** или `ca backup` / `ca restore`.

```bash
sudo ./mtls.sh ca backup --output /tmp/my-backup.tar.gz
sudo ./mtls.sh ca restore --input /tmp/my-backup.tar.gz
```

В резервную копию входят:
- Файл конфига (`~/.mtls-manager.conf`)
- База сертификатов (`~/.mtls-manager.db`)
- Список сервисов (`~/.mtls-manager.services`)
- Журнал аудита (`~/.mtls-manager.audit.jsonl`)
- Все файлы CA (сертификаты, ключи, промежежуточные CA, CRL и т.д.)

## Журнал аудита

Каждое действие (создание CA, выпуск/отзыв/удаление сертификата, добавление/удаление сервиса, изменение конфига, управление пользователями, backup/restore) записывается в `~/.mtls-manager.audit.jsonl` в формате JSONL.

```bash
sudo ./mtls.sh audit
sudo ./mtls.sh audit --last 10
```

Каждая запись содержит: временную метку, действие, исполнителя (имя пользователя) и опциональные детали.

## Режимы bundle

### `shared` (по умолчанию)

Все сервисы используют один `clients-bundle.crt`, содержащий промежежуточные CA всех активных (не отозванных) клиентов.

### `per-service`

Каждый сервис получает свой bundle-файл `clients-bundle-<service>.crt`, содержащий только промежежуточные CA клиентов этого сервиса. Это обеспечивает изоляцию между сервисами.

| Файл | Формат | Содержимое |

| `~/.mtls-manager.conf` | KEY="value" | Пути, срок по умолчанию, настройки уведомлений |

```
/etc/traefik/

│   ├── ca.key                    ← приватный ключ CA (600)
```

## Промежуточные CA (per-client)

Для каждого клиентского сертификата создаётся **отдельный промежуточный CA** (intermediate CA), подписанный корневым CA.

Цепочка доверия:
```
Root CA  →  Int-CA (alice)  →  client.crt (alice)
Root CA  →  Int-CA (bob)    →  client.crt (bob)
```

Зачем это нужно:

1. **Гранулярный отзыв**: при отзыве сертификата alice из bundle просто исключается `int-ca-alice.crt`. Bob при этом не затронут.
2. **Без CRL на стороне Traefik**: не нужно настраивать проверку списков отзыва — достаточно перестроить bundle.
3. **Мгновенный эффект**: Traefik подхватывает обновлённый bundle без перезагрузки (при включённом file provider).

## Patch-режим

При добавлении сервиса в режиме `patch` скрипт вносит изменения в указанный YAML-файл Traefik.

**Алгоритм патча** (реализован на Python3 через heredoc):

1. Парсит YAML построчно (без зависимостей — только стандартный Python)
2. Ищет секцию `routers:` и в ней роутер с указанным именем
3. Внутри роутера находит блок `tls:`
4. Добавляет строку `options: mtls-<service>` (или заменяет существующую)

При удалении сервиса строка `options: mtls-<service>` удаляется из файла.

Возможные результаты патча: `patched`, `already_patched`, `not_found`.

## Генерация Traefik-конфига

Функция `do_gen_traefik()` создаёт файл `<TRAEFIK_DYNAMIC_PATH>/<OUTPUT_FILE>` со следующей структурой:

```yaml
# Generated by mtls-manager — 2025-01-15 10:00:00
# DO NOT EDIT MANUALLY

tls:
  options:
    mtls-myapp:
      clientAuth:
        caFiles:
          - "/etc/traefik/certs/mtls/clients-bundle.crt"
        clientAuthType: RequireAndVerifyClientCert
      minVersion: VersionTLS12

http:
  routers:
    myapp-mtls:
      rule: "Host(`myapp.example.com`)"
      entryPoints:
        - websecure
      service: myapp-mtls
      tls:
        options: mtls-myapp

  services:
    myapp-mtls:
      loadBalancer:
        servers:
          - url: "http://172.17.0.1:3000"
```

Секции `http.routers` и `http.services` генерируются **только** для сервисов в режиме `new`. Для `patch`-сервисов создаётся только блок `tls.options`.

После генерации YAML структурно проверяется (наличие секции `tls:`, отсутствие табов и т.д.).

## Очистка браузерных хранилищ

При каждом выпуске нового `.p12` браузер сохраняет в своё хранилище не только клиентский сертификат, но и промежуточный CA. Это может привести к накоплению устаревших записей.

**Linux (Chrome):**
```bash
apt install libnss3-tools
certutil -L -d /home/<user>/.local/share/pki/nssdb/
certutil -D -d /home/<user>/.local/share/pki/nssdb/ -n "opensophy - mTLS-Manager"
```

**Windows (Chrome/Edge):**
```powershell
Get-ChildItem -Path Cert:\CurrentUser\CA | Where-Object { $_.Subject -like "*opensophy*" } | Remove-Item
```

## Известные ограничения

- **Нет поддержки ECDSA**: скрипт использует RSA (2048 бит для клиентов, 4096 для CA). ECDSA не поддерживается.
- **OCSP/CRL не настраивается**: отзыв реализован через bundle, не через стандартные механизмы CRL/OCSP.
- **Python3-парсинг YAML**: патчинг конфигов Traefik реализован построчным разбором, а не через yaml-библиотеку. Нестандартные форматы YAML могут обрабатываться некорректно.
- **Уведомления вручную**: `cert scan` нужно запускать вручную или через cron — скрипт не работает как демон.
